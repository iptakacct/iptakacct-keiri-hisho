# 決算の仕組み 段階2（資料の読み取り・確認・承認）設計書

- 作成日：2026-09-17
- ステータス：設計承認済み（実装計画は未作成）
- 親の設計書：`docs/superpowers/specs/2026-09-16-kessan-without-accounting-system-design.md`（§6 資料→帳簿、§12 段階2）
- 前提：段階1（`.claude/scripts/kessan/` の取り込み・登録・検算・試算表）は完了済み

## 1. 目的

通帳・明細のPDF/画像、領収書・請求書のPDF/画像、Excel（出納帳・売上表等）を、AIが読み取って帳簿の候補にし、人の確認・承認を経て段階1の `post` で登録できるようにする。

原則は段階1と同じ：**AIは読み取りと判断だけ。数字の検算・突き合わせ・二重防止はスクリプトが行う。**

## 2. 前提となる事実（オーナー確認済み）

マイクロ法人の領収書・請求書の支払方法は、次の4つがすべて起こりうる。

- 役員が個人で立替（法人の明細に出ない → 新しい仕訳。貸方 役員借入金）
- 法人の口座・法人カード（明細に同じ支払が出る → 新しい仕訳にせず、明細の行に証憑として付ける）
- 法人の現金（新しい仕訳。貸方 現金）
- 請求書で後払い（支払った明細の行に付ける。期末未払は段階3の材料）

→ 証憑1枚ごとに「新しい仕訳か、明細の行に付けるか」を見分けることが段階2の中心。誤ると二重計上になる。

## 3. 方式

AIは資料ごとに**読み取り結果ファイル（JSON）**を書くだけとし、スクリプト `import-extracted` が形式チェック・残高検算・期間チェック・明細との突き合わせ・二重防止を行ってから `staging.csv` に入れる。AIが `staging.csv` を直接編集することはない（科目候補の書き込みも `set-accounts` コマンド経由）。

採らなかった案：AIが staging を直接編集する（検算・突き合わせがAIの注意力頼みになる）、OCRライブラリ（手書き・写真に弱く導入が重い）。

## 4. 全体の流れ（`kessan-books` スキル）

```
①inbox-status：inbox/ の未処理資料を一覧（取り込み記録に無いファイル）
②AIが資料を読み、extracted/<資料名>.json を書く（CSVは従来どおり import-bank）
③import-extracted：検証・突き合わせ・二重防止をして staging.csv へ
④set-accounts：AIが要確認行に科目候補と理由を付ける（スクリプトが検証して反映）
⑤review：確認用Excelを出し、要点をチャットで報告
⑥承認：Excel（apply-review）またはチャット（approve）
⑦post（段階1）：登録＋検算、結果を報告
⑧日報（work/daily/）に記録
```

## 6. 読み取り結果ファイルの形式

共通：`資料`（inbox/ からの相対パス）、`種類`（`通帳` / `領収書` / `請求書` / `出納帳`）。金額は円の整数、日付は `YYYY-MM-DD`。元の表記は `日付原文` に残す。

### 通帳
```json
{
  "資料": "inbox/通帳-2025-04.pdf",
  "種類": "通帳",
  "口座ID": "main",
  "ページ": [
    {"ページ番号": 1, "繰越残高": 1000000,
     "行": [{"日付": "2025-04-01", "日付原文": "07-04-01", "入金": 100000, "出金": 0, "摘要": "フリコミ カ）テスト", "残高": 1100000}]}
  ]
}
```

### 領収書・請求書
```json
{
  "資料": "inbox/領収書-0001.jpg",
  "種類": "領収書",
  "日付": "2025-04-10", "日付原文": "2025年4月10日",
  "金額": 3300, "取引先": "テスト文具店", "内容": "文房具",
  "支払方法の推定": "不明",
  "科目候補": "消耗品費", "補助候補": "",
  "自信度": "高", "メモ": ""
}
```
`支払方法の推定`：`口座` / `カード` / `現金` / `立替` / `後払い` / `不明`。
任意で `支払期日`（`YYYY-MM-DD`。請求書に支払期限が印字されていれば書く。期末後の期日もありうるので事業年度の範囲は見ない）。段階3で未払を管理する材料として `evidence.csv` に残すだけで、突き合わせには使わない。

### 出納帳（Excel等）
```json
{"資料": "inbox/出納帳.xlsx", "種類": "出納帳", "科目": "現金", "補助": "",
 "行": [{"日付": "2025-04-03", "入金": 0, "出金": 1200, "摘要": "切手", "残高": 48800}]}
```
前期決算書は取り込まない。AIが `opening-balances.csv` の案を出し、人が確認して反映する。

### 形式エラー
必須項目の欠落、日付・金額が読めない、期間外の日付、未登録の口座ID・科目、`kessan-sources.yaml` の `accounts` に登録されていない出納帳の（科目, 補助）（登録が無いと出納帳の行が突き合わせ・二重計上の検知の相手にならないため） → **そのファイル全体を取り込まず**、ファイル名と理由を報告する。AIが直して再実行する。

## 7. 通帳のページ検算

- ページ内：`繰越残高 + 入金 − 出金 = 各行の残高` を順に確認する（繰越残高が無いページは最初の行を起点にする）。
- ページ間：前ページの最後の残高と、次ページの繰越残高（無ければ最初の行から逆算した直前残高）が一致するか。
- 合わないページの行は、止めずに `読み取り信頼度=低`・`要確認理由=ページの残高が連続しない` で取り込む。
- 取り込み元IDは銀行CSVと同じ作り方（口座ID・日付・入金・出金・正規化した摘要・残高・出現回数）。**同じ取引をCSVと通帳の画像の両方で受け取っても二重に入らない。** 摘要の表記違いでIDが一致しない場合は、段階1の「取り込み済みの明細と日付・金額が一致（二重取り込みの疑い）」で要確認になる。
- 明細残高は `statement-balances.csv` に記録する（検算3の照合相手）。

## 8. 証憑と明細の突き合わせ

- 同じ回の取り込みでは、明細（通帳・出納帳）を先に、証憑（領収書・請求書）を後に処理する（各グループ内は渡された順序のまま）。証憑を先に処理すると、まだ明細が無く突き合わせ候補が見つからないまま新しい仕訳を作ってしまうため。
- 相手：`kessan-sources.yaml` に登録した口座・カード・現金の（科目, 補助）について、支払側（貸方）の行。journal.csv と staging.csv の両方。
- 条件：金額が同じ、日付が証憑の日付の前後7日以内、その行にまだ証憑が付いていない。
- 候補が1つ：新しい仕訳は作らない。`evidence.csv` に対応を記録する。その行が staging にあり相手科目が空なら、科目候補・補助候補・取引先を入れる（`要確認理由` に「証憑と一致」を**追記**する。既にある理由（「ページの残高が連続しない」「二重計上の疑い」等）は消さない。外すのは相手科目が埋まった「相手科目未設定」だけ。証憑の`自信度`が低ければ、その行の`読み取り信頼度`も低にする）。**journal.csv は書き換えない。**
  - 金額・日付だけで一致した可能性があるので、証憑の `取引先` が明細の `摘要` に（法人格略語を読み替えても）含まれないときは、突き合わせは行ったうえで「取引先名が摘要に無い（突き合わせ先を確認）」を追記する。
- 候補が複数：新しい仕訳は作らず、証憑を「突き合わせ先が複数」として要確認の一覧に出す（`evidence.csv` には未確定として記録）。
- 証憑から作る新しい仕訳の行には、`取り込み元ID=receipt:<証憑ID>` を付ける（`set-accounts`・`approve` の対象にでき、段階1の重複検知も効く）。
- 候補なし：会社の既定の支払方法（`accounting-rules.md`「領収書の既定の支払方法」を `kessan-sources.yaml` の `receipt_default` として機械可読にも持つ）で新しい仕訳の候補を作り、`要確認理由=明細に該当なし` とする。既定が無ければ貸方を空けて要確認。
  - `支払方法の推定` が `立替` → 貸方 役員借入金、`現金` → 貸方 現金、`後払い` → 新しい仕訳は作らず「未払候補」として `evidence.csv` に記録（段階3の材料）。
  - **請求書（種類=請求書）は、支払方法の推定が `不明` でも `receipt_default` を適用しない**。銀行振込での支払と二重計上になりやすいため、`後払い` と同じ「未払候補」にする（`receipt_default` は領収書のみに適用する）。
- 明細を先に取り込んでも、証憑が後から来るとは限らない（証憑を先に取り込んでから、後で明細が来る場合もある）。この逆方向の突き合わせは、明細側の取り込み（`bank_import.stage_statement_rows`。CSV・通帳・出納帳の共通部分）で行う：新しく取り込む支払側（出金）の行について、`evidence.csv` に金額が同じで日付が前後7日以内（両端含む）の証憑があれば、
  - 状態が「新規仕訳」→ `要確認理由`に「証憑から計上済みの仕訳と金額・日付が近い（二重計上の疑い）」を追記（二重計上の可能性を知らせる）
  - 状態が「未払候補」→ `要確認理由`に「未払候補の証憑と金額が一致（支払の可能性）」を追記（未払の証憑にようやく支払が付いた可能性を知らせる）
  - 既存の`要確認理由`は消さず「／」で連結する。
  - 「新規仕訳」の証憑に当たったときは、その証憑から作った行（`receipt:<証憑ID>`）がまだ staging にあり未承認なら、そちらにも「明細にも同額の支払がある（二重計上の疑い）」を追記する（二重計上の疑いを両側の行に付ける）。
- **要確認理由は追記だけ**：スクリプトが付けた理由は、どのコマンドでも消さない（`common.add_reasons` で「／」区切りの部分として追記し、同じ部分は重ねない）。スクリプトが外すのは「相手科目未設定」だけで、`set-accounts` や証憑の突き合わせで相手科目が埋まったとき（と、「二重取り込みの疑い」を付けるとき）に限る。

### evidence.csv の列
`証憑ID, 証憑ファイル, 種類, 日付, 金額, 取引先, 内容, 科目候補, 補助候補, 状態（明細に対応／新規仕訳／複数候補／未払候補／破棄）, 取り込み元ID, 取り込み日時, 支払期日, 支払方法の推定, 自信度`

末尾の `支払期日`・`支払方法の推定`・`自信度` は読み取り結果の値をそのまま残す（段階3の未払管理の材料）。`破棄` は、証憑から作った行（`receipt:`）を `discard` で破棄したもの。

## 9. 証憑の二重取り込み防止

- 証憑ID＝「日付・金額・取引先（NFKC正規化し空白を除いたもの）」のハッシュ。
- **同じ資料ファイル**（`extracted/<資料名>.json` の「資料」パス）の再取り込みは、`import-log.csv` に記録済みのファイル名と照合して止める（件数0になる）。これは今まで通り。
- **別の資料ファイルが同じ証憑ID（同じ日付・金額・取引先）を持つ場合は、取り込みを止めない**（例：同じ領収書を撮り直して2つのファイルになった場合）。証憑IDに `-2`・`-3` …を付けて重複しない一意なIDにしたうえで、通常の証憑と同じように明細との突き合わせ・新しい仕訳の作成を行い、その結果（明細に一致した行、または新しく作った仕訳の行）の`要確認理由`に「証憑の重複の疑い（証憑ID <元の証憑ID>）」を追記する（既存の理由は消さず「／」で連結）。「突き合わせ先が複数」「未払候補」のように行に直接書けない場合は、`import-extracted`の結果に重複ファイルの一覧として残す。
- 取引先の読み取りが揺れて証憑IDが違う場合に備え、日付・金額が同じ既存の証憑があれば `要確認理由`に「証憑の重複の疑い（証憑ID <既存の証憑ID> と日付・金額が一致）」を追記する（これも既存の理由を消さず連結する）。この確認は突き合わせの結果（明細に対応・新規仕訳・複数候補・未払候補）によらず行い、理由を書ける行が無いとき（複数候補・未払候補・登録済みの明細に対応した等）は `import-extracted` の結果に一覧として出す。

## 10. 科目候補の書き込み（set-accounts）

- 入力：`{取り込み元ID: {借方科目, 借方補助, 貸方科目, 貸方補助, 取引先, 判定, 要確認理由}}` のJSON。
- スクリプトの検証：科目がマスタにある、対象行が staging にある、承認済みの行を上書きしない、`判定=確立済み` はAIからは指定できない（指定されたらエラー）。1件でも不正なら何も反映しない。
- `要確認理由` は上書きしない。AIが書いた理由は既存の理由に**追記**され、スクリプトが付けた理由（二重計上の疑い等）は消えない（空文字を書いても消えない）。借方科目・貸方科目の両方が埋まったときだけ「相手科目未設定」を外す。
- 取り込み元IDの無い行（手入力等）は対象外（その行は人が確認する）。

## 11. 確立済みパターンの自動承認

- `context/company/kessan-patterns.yaml`：`摘要キーワード` または `取引先`（正規化して部分一致）→ `科目・補助`、任意で `金額の範囲`。
- 対象は明細の行（`bank:`）だけなので、`取引先` も**明細の `摘要` とだけ**照合する（法人格略語を読み替える）。staging.csv の `取引先` 欄はAIが `set-accounts` で書けるので照合に使わない（AIの書いた取引先で自動承認させない）。
- `import-extracted` / `import-bank` / `set-accounts` の後にスクリプトが照合し、一致した行だけ `判定=確立済み`・`承認=済` にする。**AIの判断では自動承認しない。**
- パターンの追加はオーナーの承認後（`accounting-rules.md` の既存運用と同じ）。

## 12. 確認用Excelと承認

- `review`：`output/review-YYYYMMDD.xlsx` を出す。要確認の行を上に、列は `取り込み元ID・日付・金額・摘要・借方・貸方・証憑ファイル・要確認理由・読み取り信頼度・承認・修正メモ`。読み取り信頼度が低い行と「明細に該当なし」の行は色付け。別シートに「突き合わせ先が複数」「未払候補」「読めなかった資料」の一覧。
- `apply-review`：Excelの `承認=済` を staging.csv に反映する（取り込み元IDで対応。Excel側で科目等を書き換えても反映しない＝承認だけを読む）。`修正メモ` がある行は承認せず、一覧を出してAIが読んで直す。staging.csv をExcelで直接開かなくて済むので、日付形式・文字コードの問題を避けられる。
- 色付けは、「二重計上の疑い」「二重取り込みの疑い」「証憑の重複の疑い」「支払の可能性」「取引先名が摘要に無い」を含む行を赤（最優先）、読み取り信頼度が低い行をオレンジ、「明細に該当なし」の行を黄色にする。
- `apply-review` は、`承認` 欄に「済」以外（「OK」「○」等）が書かれた行の件数も報告する（承認はしない）。Excelで「済」を消しても承認は外れない（外すのは `修正メモ`）。
- `approve --review-file <確認用Excel> --numbers N …`：チャットで「3番以外OK」等と番号で言われたときに使う。スクリプトが確認用Excelで番号を取り込み元IDに置き換え、`apply-review` と同じ指紋の確認をする（Excel出力後に内容が変わった行は承認せず一覧に出す）。
- `approve --ids …`：取り込み元IDの一覧を受け取り `承認=済` にする（番号で言われたときは使わない。指紋の確認が無いため）。
- どちらも、反映後の登録は段階1の `post`。

## 13. 段階1からの持ち越し修正（計画の最初の作業）

1. post が staging の日付を空白を除いた値で journal に書く
2. post の取り込み記録の読み込みを書き込み前に行い、登録後に文字コードで失敗しない
3. 「登録済み・検算NG」の終了コードを 3 にし、argparse の使い方エラー（2）と区別する（README も更新）
4. `parse_amount` が全角数字を読める（NFKC）
5. 法人名略語（`company-name-abbreviations.md`）と摘要を照合するときは両側を正規化する（`match.py` の取引先照合に適用）

## 14. エラー時の扱い

- 読めない資料（ぼやけ、パスワード付きPDF等）：読み取り結果ファイルを作らず、スキルが「読めなかった資料」として報告する。
- 形式が崩れた読み取り結果ファイル：取り込まず理由を出す。
- すべてのコマンドは段階1と同じく、書き込み前に検証し、失敗時は何を書いた／書いていないかが分かる `KessanError` を出す。

## 15. テスト

- 単体テスト（pytest）：読み取り結果の形式チェック、ページ検算（ページ内・ページ間）、CSVと通帳で同じ取り込み元IDになること、突き合わせ（1件・複数・なし・既に証憑付き・日付の境界7日）、証憑の二重防止、`set-accounts`（確立済みの拒否・承認済みの保護）、パターン照合と自動承認、Excel出力と `apply-review` の読み戻し、`approve`。
- テスト用データ：架空の会社の読み取り結果JSONとExcel（`tests/` 配下。実クライアント情報は入れない）。
- 手動確認：架空の通帳・領収書の画像を数枚作り、スキルを実際に通して、AIの読み取りから登録・検算までを1回確認する。

## 16. 対象外（段階2では作らない）

- 期末の未払金・未収金の計上（段階3。未払候補は `evidence.csv` に残すだけ）
- 売上表からの売掛金計上の自動化（出納帳と同じく明細行として取り込むところまで）
- 自社口座間の振替の対応付け（検算3で残高の不一致として気づける。必要になったら追加）
- 会社別の科目追加ファイル（段階3で決める）

## 17. 取り込みの取り消しと行の破棄（最終レビューで追加）

どちらも、全部を検証してから書き（拒否する理由が1つでもあれば何も変えない）、書く前に対象のCSVが書き込めるか確かめる。承認済みの行・帳簿（journal.csv）に登録済みの行には触らない。

- `unimport --source inbox/<資料> [inbox/<資料> ...]`：読み違えた資料の取り込みを取り消す。staging.csv のその資料の行（`証憑ファイル`）、statement-balances.csv・import-log.csv の記録（`ファイル名`）、evidence.csv の証憑（`証憑ファイル`）を消す。`--source` は複数並べられ、全部を検証してからファイルごとに1回で書く。
  - 資料の記録名：`import-bank` も、年度フォルダの `inbox/` の中の銀行CSVは `inbox/…`（`/` 区切り）で記録する（`inbox/` の外から取り込んだものだけファイル名）。取り込み元IDの作り方は変えない（ファイル名を材料にしない）。
  - `--source` は記録名と完全に一致する資料だけを指す。フォルダを含まない指定は、ファイル名が同じ記録が1件ならそれを指し、複数あれば候補を挙げて拒否する。
  - 同じ口座ID（口座・`出納帳:…`）で対象期間が重なる、取り消さない取り込み済み資料があれば拒否する（明細の行は取り込み元IDで二重に入らないため、どちらか一方の資料の分として記録されている）。重なる資料も `--source` に並べれば取り消せる。領収書・請求書（口座ID欄＝種類）は対象外。
  - 明細に対応した証憑を取り消すときは、明細の行は消さず「証憑と一致」を外す。その行が未承認で、借方科目・借方補助・取引先がまだ証憑の科目候補・補助候補・取引先のままなら空に戻して「相手科目未設定」を追記する。科目が変えられていて戻さない行には「証憑の取り消し後（科目を確認）」を追記する（理由の無い行として確立済みパターンで自動承認されないように）。
  - 拒否：その資料の行や対応する明細行が承認済み（修正メモで承認を外してから）、帳簿に登録済み（取り消せない）、その資料の明細行に別の資料の証憑が付いている（先に証憑を取り消す）。
  - 取り消した後は、読み取り結果を直して `import-extracted` で取り込み直せる。
- `discard --ids … --reason …`：オーナーが確認した重複など、不要な未承認行を取り込み元IDで捨てる。`discard-log.csv`（日時, 取り込み元ID, 日付, 金額, 摘要, 理由）に記録し、証憑から作った行（`receipt:`）の証憑は `evidence.csv` の状態を「破棄」にする。承認済み・登録済みの行、証憑が付いた明細行は拒否する。
  - 破棄した行は取り込み直しても入れない：すべての取り込み（`import-bank`、`import-extracted` の通帳・出納帳・領収書・請求書）で、取り込み元IDが `discard-log.csv` にある行は staging.csv に入れず、件数を「破棄済みのため入れなかった行：N件」と表示する。明細の行は、その残高がこの資料の分として未記録なら記録し、他の行の要確認理由の材料にしない。証憑は仕訳の候補を作らず、evidence.csv には状態「破棄」で記録し、import-log.csv には記録する（資料は処理済み）。
