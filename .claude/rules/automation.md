# 自動化スクリプトの型

新しく自動化スクリプト（`.claude/scripts/`配下のスケジューラー用スクリプト等）を作るときは、必ず以下を入れる。

1. **エラーハンドリング**：失敗を握りつぶさない（`set -eu`、`$ErrorActionPreference = "Stop"`等）
2. **実行ログ**：いつ動いて何をしたか分かるようにする（Slack投稿・ログファイルへの記録など）
3. **失敗時の通知先**：失敗した時に何が起きるか・誰にどう伝わるかを明確にする
   - **Slackへの通知は、`claude -p`経由でオーナー本人のSlackアカウントとして投稿する設計にしない**。Slackの仕様で自己送信メッセージは通知が抑制されるため、本人に気づいてもらえない。Bot経由のIncoming Webhook（`.env`の`GENERAL_SLACK_WEBHOOK_URL`等）を使い、必要ならメンション（`<@SLACK_MENTION_USER_ID>`）を付ける

その他の運用ルール:
- cron・タスクスケジューラー等での定期実行を設定する前に、必ず手動実行で1回成功を確認する
- 認証情報はスクリプトに直書きせず、環境変数または設定ファイル（`.gitignore`・`deny`対象）に置く

## PowerShellスクリプトで`claude.exe`の出力を変数に取り込む場合の文字化け対策

`$output = & "claude.exe" -p $prompt ...` のように、`claude -p`の標準出力（UTF-8）をPowerShell変数に取り込んで加工するスクリプトでは、**取り込み前に明示的にUTF-8デコードを指定しないと、日本語部分だけが文字化けする**。

- 原因：PowerShellが子プロセスの標準出力を読み取る際のデコードは`[Console]::OutputEncoding`に従うが、これがシステムのANSIコードページ（日本語Windowsでは932=Shift-JIS）になっている実行環境（特にタスクスケジューラー経由）では、UTF-8バイト列をShift-JISとして誤デコードする
- 症状の見分け方：英数字は無事なのに日本語部分だけ意味不明な記号・半角カタカナ（`ｦｧｨｩｪｫ`等）だらけになっていたら、このパターンを疑う
- 対策：スクリプト冒頭（claude.exeを呼ぶ前）に以下を必ず入れる
  ```powershell
  [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
  $OutputEncoding = [System.Text.Encoding]::UTF8
  ```
- Slack Webhook送信時のエンコード処理とは別の、その手前の「claude.exeの出力を読み取る」段階の問題なので、送信側だけ直しても再発しうる

## BashスクリプトからPythonを呼ぶ場合の文字化け対策

Bashラッパースクリプトが`python`の標準出力を`> file 2>&1`のようにファイルへリダイレクトして後で読む設計では、**Windows環境でPythonの標準出力エンコーディングがcp932にフォールバックし、日本語部分が文字化けする**ことがある。

- 症状の見分け方：同じログファイル内で、Bashスクリプト自身が直接書いた行（正常なUTF-8）と、Python経由で取り込んだ行（文字化け）が混在する
- 対策：Pythonを呼び出す前に環境変数で明示的にUTF-8を強制する
  ```bash
  export PYTHONIOENCODING=utf-8
  export PYTHONUTF8=1
  ```
- 似た構成（Bash＋Python、標準出力をファイル/変数に取り込む）の新規スクリプトを作る際は、最初からこの2行を入れておく

## クロスプラットフォーム対応

macOSとの並行運用を想定し、**新しく作る自動化スクリプトはWindows固有のパス・PowerShell依存を避け、macOSでも動く形にする**。

- 新規スクリプトはPowerShell（`.ps1`）ではなく、Bash等のクロスプラットフォームな手段を優先する
- パスはWindows固有の区切り文字・ドライブレター表記を避け、OS非依存な書き方にする
- 既存のWindows専用資産は、置き換えのタイミングまで無理に書き直さなくてよい

## 無人`claude -p`でclaude.aiコネクタ（MCP）を使うときの注意

- claude.aiのコネクタ（`mcp__claude_ai_*`等）は、タスクスケジューラー等からの非対話`claude -p`でも使える（`claude mcp list`で「Connected」なら可）。ただしマネーフォワード会計の読み取りは、無人でも自前API（`mf-api-post`の`read`等）で行うのが本則（`mf-api-post`は現状読み取り専用で、登録は`mfc_ca`）
- 同名のローカルMCPサーバーが未認証で残っていると、**軽いモデル（haiku）はそちらに惑わされて「MCP認証未接続」と誤報告する**。対策：プロンプトに「`mcp__claude_ai_`で始まるツールだけを使う・ローカルの`authenticate`系は使わない」と明示し、モデルはsonnetにする
- `claude -p`をパイプに繋ぐ場合は`< /dev/null`で標準入力を閉じる（3秒待ちの警告が出て遅くなるため）

## 出力をパースする`claude -p`は、リポジトリの外（空のディレクトリ）から起動する

`claude -p`は**起動時のカレントディレクトリが属するプロジェクトの設定・hooks・CLAUDE.mdを読み込む**。スクリプトが自分のリポジトリ内から`claude -p`を呼ぶと、対話作業向けに入れたhooksが無人実行にも発火し、出力を壊すことがある。

- 実例：`claude -p`は1ターン目で正しいJSONを返していたのに、グローバルのStop hook（テスト実行）が発火し、テスト環境の不備で失敗→完了をブロック。モデルは正しい回答を捨てて約30ターン環境の修復を試み続け、最終的な標準出力が空になった。呼び出し側は「JSON本体が見つかりません」というパースエラーしか見えず、原因がhookにあると分からなかった
- **症状の見分け方**：`claude -p`が**終了コード0なのに標準出力が空／JSONが無い**。`--output-format json`を付けて実行すると`result`が`""`、`num_turns`が異常に多い（1で済むはずの質問に20〜30）、`permission_denials`にスクリプトと無関係なツール使用が並ぶ。所要時間とコストも桁違いになる
- **対策**：出力をパース・加工する用途の`claude -p`は、`subprocess`の`cwd`に空の一時ディレクトリを渡して起動する。あわせて`stdin`も閉じる。プロジェクトの文脈を読ませる必要が無い純粋な分析・変換用途なら、読み込むコンテキストが減って速度・コストの面でも有利
- **例外**：このリポジトリのCLAUDE.md・rules・ファイルを読ませること自体が目的の`claude -p`は、リポジトリ内から起動してよい。ただしその場合も、**そのリポジトリで発火するhooks（特にStop hook）が無人実行を妨げないか**を確認する
- **新しくhooksを足すときの逆向きの注意**：Stop hookのようにモデルの完了をブロックするフックは、対話セッションだけでなく、そのディレクトリで動く全ての`claude -p`にも効く。ブロック系のフックを追加・変更したら、`claude -p`を使う自動化が壊れていないかを確認する

## 無人の`claude -p --chrome`でブラウザ操作をさせるとき

APIに口が無く、ブラウザのログインが要る取得（例：給与システムの明細PDF。OAuthのアクセス権ではログイン画面へリダイレクトされる）は、無人の`claude -p --chrome`にChromeを操作させれば自動化できる。

- **前提はChromeが起動していて、対象サービスに正しいアカウントでログインしていること**。満たせないときは失敗として通知し、次の実行で再試行する作りにする
- **判定・照合はスクリプト側（Python等）で行い、Claudeにはブラウザ操作だけをさせる**。取得したファイルの中身（氏名・対象月など）も、Claudeの報告を信じずにプログラムで照合する
- ⚠️ **何の業務か書かずに「このコードをそのまま実行して結果だけ返せ」と指示すると断られる**。ログイン済みセッションを使って個人情報を直接取る書き方は「認証セッションの流用」と判断された。**誰が・何のために・どの権限で行う作業かを、事実どおり指示文に書く**。取得も、画面にあるリンクをダウンロードとして開くだけの素直な書き方にする
- ⚠️ **サーバーが`Content-Disposition`でファイル名を付けると、`<a download="名前">`の名前は無視される**。回収側は、サービスが付ける名前（同名があればChromeが付ける「 (1)」も含む）で探す。ダウンロードフォルダには過去に手で落とした同種のファイルも残っているので、**更新日時で新しいものだけに絞る**
- Chromeは同じサイトからの2件目以降の自動ダウンロードを止める（無音）。Chromeの設定「自動ダウンロード」の許可サイトに、本人に1回追加してもらう（設定の変更はClaudeが行わない）
- 起動は空の一時ディレクトリから（上の節と同じ）。所要は1回30〜80秒・約$0.1

## Windowsタスクスケジューラーに登録するときの型（Windows環境のみ）

### `bash.exe`は`bin\bash.exe`＋`-lc`＋POSIX形式パスで登録する

- `Execute: C:\Program Files\Git\usr\bin\bash.exe`、`Arguments: "<スクリプトのパス>"`（`-lc`無し）で登録すると、そのプロセスのPATHに`/usr/bin`等が含まれず、スクリプト内の`dirname`・`date`・`bash`が軒並み「command not found」になる。症状：`LastTaskResult`が`1`で、スクリプト自身のログに新しい行が一切追加されない（ログパスの算出に失敗してログ出力自体ができない）
- **対策**：`Execute: C:\Program Files\Git\bin\bash.exe`、`Arguments: -lc "<スクリプトのパス>"`（ログインシェル）で登録する。`bin\bash.exe`と`usr\bin\bash.exe`はどちらも実在するので紛らわしい
- **`-lc`のスクリプトパスをWindows形式（ドライブレター付きのバックスラッシュ区切り）で書くと、MSYS bashの引数解析でバックスラッシュが消えてパスが壊れる**（`LastTaskResult`が`127`）。必ずPOSIX形式（`/c/<パス>/foo.sh`）で書く。「型どおりに直したのにまだ`LastTaskResult`が0にならない」場合は、パス形式も疑うこと
- 登録直後に`Start-ScheduledTask`で1回強制実行し、`Get-ScheduledTaskInfo`の`LastTaskResult`が`0`であることと、**スクリプトのログに新しい行が追加されていること**の両方を確認する（手動実行の成功だけでは、Task Scheduler固有のPATH問題を検知できない）

### `New-ScheduledTaskSettingsSet`の既定はバッテリー駆動中に起動しない

既定で`DisallowStartIfOnBatteries = True`・`StopIfGoingOnBatteries = True`になる。ノートPCを電源に繋いでいない時間帯にトリガーが来ると、タスクは実行されず**Stateが`Queued`のまま**になる。

- 症状：`Start-ScheduledTask`してもStateが`Queued`から動かず、ログに1行も増えない。`LastTaskResult`は前回の値（`0`）のままなので、**結果コードだけ見ていると成功したように見える**。`267014`（`SCHED_S_TASK_TERMINATED`）は、`StopIfGoingOnBatteries = True`のまま電源が抜けて途中で止められたときの値
- 対策（新規登録時）：`New-ScheduledTaskSettingsSet -StartWhenAvailable -DontStopIfGoingOnBatteries -AllowStartIfOnBatteries`を付ける
- 既存タスクの直し方（作り直さずに設定だけ変える）：
  ```powershell
  $s = (Get-ScheduledTask -TaskName '<タスク名>').Settings
  $s.DisallowStartIfOnBatteries = $false
  $s.StopIfGoingOnBatteries     = $false
  $s.StartWhenAvailable         = $true
  Set-ScheduledTask -TaskName '<タスク名>' -Settings $s
  ```
  直したら強制実行し、`LastTaskResult`が`0`になることと**ログに新しい行が増えること**の両方を確認する

### Windows Updateの夜間再起動で「ログイン中だけ動く」タスクが飛ぶ

`LogonType = Interactive`（ログイン中だけ動く）のタスクは、Windows Updateの夜間自動再起動で朝ログインするまでログオフ状態になり、その間のトリガーは実行されない。`StartWhenAvailable`があっても、ログイン後に追いかけて動かない。

- 症状：`Get-ScheduledTaskInfo`の`NumberOfMissedRuns`が1以上、`NextRunTime`が翌日、ログに当日の行が無い。システムログのID 1074（`TrustedInstaller.exe`・`MoUsoCoreWorker.exe`による再起動）で確かめる
- 対策（1日1回で、取りこぼすと困るもの）：同じスクリプトに「その日の本番が既に動いていれば何もせず終わる」引数（`--catch-up`等）を足し、ログオン時トリガー（5分遅延）の別タスクで起動する

### 繰り返しトリガーのタスクはスリープ復帰時に同時起動することがある

`MultipleInstances`が`IgnoreNew`でも、PCがスリープから復帰した直後に、同じ秒で2〜3本同時に起動することがある。

- 症状：スクリプトのログに同一秒の「開始」行が複数本並ぶ。時刻が毎時ちょうどではなく半端（復帰した時刻）。同じ状態ファイル・同じ認証情報を奪い合い、**使い捨てのリフレッシュトークンは必ず後発が失敗する**。同じSlack通知が2回飛ぶ、状態ファイルの更新が片方に潰される、といった形でも出る。**同じログファイルへの同時追記は行が壊れる**ので、「同一秒の行が壊れている」ときはまず二重起動を疑う
- 対策：**定期実行するスクリプトは、最初に排他ロックを取り、先客がいれば静かに終わる**。`flock`はGit for Windowsに入っていないので、`mkdir`の原子性を使う。異常終了でロックが残っても、一定時間（既定30分程度）を過ぎれば次の起動が引き継ぐ作りにする
- ⚠️ 30分を超えて走りうるスクリプトは、ロックを「古い」とみなす秒数を延ばす（目安は想定最長時間の2倍）。既定のままだと、長い処理の最中に次の起動がロックを引き継いで同じ処理が並走する。あわせてタスクの`-ExecutionTimeLimit`をそれより長くしておく
- ⚠️ ロックの解放を`EXIT`トラップで行う場合、後から別の`trap ... EXIT`を張るとロックの解放が上書きされて残る。後からトラップを張るなら、その中でロック解放も呼ぶ
- ⚠️ 長時間走るスクリプトは、進み具合をログへ逐次書く。最後にまとめて結果を出す作りだと、「止まっているのか重いのか」を外から判断できない
- ⚠️ `.ps1`は**UTF-8 BOM付き**で保存する。Windows PowerShell 5.1はBOM無しUTF-8をcp932として読むため、日本語コメントが化けて構文エラーになる。`head -c 3 <file> | od -An -tx1`が`ef bb bf`になることを確かめる

## 定期処理から commit・push するときはパスを限定する

`git commit -m`をパス指定なしで呼ぶと、対話セッションでステージ済みの無関係な変更まで巻き込んで push される。また同時刻に動く2本が同時に push すると、片方が`cannot lock ref`で弾かれる。定期処理の commit は**パスを限定して**行い、ロックで直列にして push する。`pull --rebase`はしない（作業ツリーに未コミットの作業が常にあるため）。

## Slack Web APIを長時間呼び続けるスクリプトの注意

標準ライブラリ`urllib`で組んだ薄いラッパーは、HTTPError・URLErrorしか拾わず、タイムアウトも無いことが多い。数百〜数千回呼ぶ処理では次の2つが実際に起きる。

- **通信の途中切れでプロセスごと落ちる**：`http.client.IncompleteRead`、`ConnectionResetError`、`TimeoutError`はそのまま投げられる。呼び出し側がAPIエラーしか拾っていないと、数時間の処理がその1回で止まる
- **応答が返らないと永久に待つ**：タイムアウトが無いため

対策：一時的なエラー（上記の例外、HTTP 5xx）は間隔を空けて数回やり直し、駄目ならAPIエラーに変換して投げ、呼び出し側がその単位だけ飛ばして先へ進めるようにする。権限不足・チャンネルが無い等の恒久的なエラーはやり直さない。プロセスの先頭で`socket.setdefaulttimeout(60)`を設定する。

## 使い捨て（ローテーションする）リフレッシュトークンは、同時実行で必ず片方が死ぬ

マネーフォワード（クラウド請求書・クラウド会計）は、**トークンを更新するたびに新しいリフレッシュトークンを発行し、古い値をその場で無効にする**。同じ認証情報ファイルを使うプロセスが重なると、先に更新した方が勝ち、後発は必ず`HTTP 400 invalid_grant`（「The refresh token passed to the token endpoint does not exist.」）になる。

- **これは失効ではなく競合**。「認可をやり直さないと直らない」と判断して手戻りしないこと（次のサイクルでは何事もなく通る）
- **対策（2段構え）**：①排他ロックで二重起動を防ぐ ②更新に失敗したら**認証情報ファイルを読み直す**。自分が使った値と変わっていれば、勝った側の結果に乗り換える。変わっていなければ本当の失効として投げる
- freee・invoxも同じローテーション方式なので、同じ対策が要る
- 保存は必ず一時ファイル＋リネームで行う。書き込み途中で落ちると更新用のトークンを失い、**本当に認可のやり直しが必要になる**（無人スクリプトからは復旧できない）
