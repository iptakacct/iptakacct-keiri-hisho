# MCPコネクタの接続・事業者切替（全クライアント共通）

claude.aiのカスタムコネクタ（マネーフォワードMCP・freee・Slack等）は「1接続＝1事業者／1ワークスペース」で、対象を変えるには接続し直す必要がある。接続先は**アカウント単位で全セッション共有**されるため、切替は他のセッション・サブエージェントの作業に影響する。

## マネーフォワード：読み取りはMCPの事業者切替をしない

月次の読み取り（未仕訳の確認・過去仕訳の検索・月次チェック）は、自前のマネーフォワード会計API（`mf-api-post`）で会社名を指定して行い、MCPの事業者切替はしない（`mf-fee-post`・`mf-monthly-check`参照）。`mf-api-post`は現状読み取り専用なので、**登録（明細から・証憑から）だけはMCP（`mfc_ca`）で対象の会社に接続して行う**。

- 複数事業者を1つのMCP接続で横断する方法は、マネーフォワードから公式にも提供されていない（OAuth2接続では`identification_code`パラメータも無視される）。**この制約の回避策を再提案しない**。自前API（会社ごとのOAuth認可）が回避策
- MCPの事業者切替は、登録を行うときと、自前APIが使えないとき（認可切れ等）に限る。短縮策は切替の高速化ではなく**切替回数を減らすこと**：1社に接続している間にMCPで行う操作を**まとめて終わらせる**（工程ごとに全社を回ると切替回数が工程数だけ増える）。接続前にできる準備（CSV解析・登録内容の組み立て・突合）は先に済ませ、接続中はID引き当てと登録・検証だけにする
- MCPで切り替える前に、他のセッションやサブエージェントがMCPを使っていないか確かめる。切り替えるのは全員の作業が終わってから

## 接続・再接続したら接続先を必ず確認する

- マネーフォワード：`mfc_ca_currentOffice`で社名・事業者コードを確認して報告する（`output-format.md`）
- freee：`freee_current_user`または`freee_get_current_company`で会社名・会社IDを確認して報告する
- Slack：ワークスペース切替（コネクタ設定画面から切断→再連携）は他のSlack依存処理にも影響するグローバルな状態変更なので、**切り替える前・戻す前にオーナーへ一言確認する**
- 画面操作（claude-in-chrome）で事業者を切り替える場合も、**操作の前に画面の事業者名を確かめる**。ブラウザのログイン中の事業者と、自前API・MCPの接続先は別物
- ブラウザで`confirm()`・`alert()`が出るとタブごと固まる。押すJSと同じ本文の先頭で `window.confirm=()=>true; window.alert=()=>{};` を仕込む。切替ボタンは座標クリックに頼らず、URL・要素で指定する

## 仕訳の自動処理の前に「口座連携の確認」を行う

対象：`mf-fee-post`・freeeの未処理明細の登録など、指定した会社の明細をもとに仕訳を起票する作業全般。Claudeは**確認と報告まで**が基本（ログイン情報が要る再連携はオーナーが行う）。

### 銀行連携は期限切れで止まる。状態は画面で読む

銀行・カードのAPI連携には接続期間（90日程度）があり、切れても通知は出ず**明細が取れなくなるだけ**。気づかないと帳簿がその日から止まり、大きな入出金が丸ごと入っていない事故になる。入金確認で「入金はまだ」と誤答する原因にもなる。

- 期限は銀行ごとに違う。同じ会社でも、同日に登録した口座のうち一部だけが切れることがある。他行・カードの期限は実測で確かめる
- **次に切れる日は「再連携した日＋その銀行の期限」**。再連携したら、その口座と次の期限目安をインスタンスの`context/`に記録する
- **取得状態はAPIでは分からない**（`connected_accounts`は口座名しか返さず、明細の最新日からの推測は取引の少ない口座で判定できない）。**対象の会社でマネーフォワードの口座一覧（データ連携 → 登録済一覧）を開き、「最終取得日時」「取得状態」列を読む**。「正常」以外（設定エラー等）があればその場で報告する
- 取得状態が「正常」の表示のまま、最終取得が何日も前で止まっていることがある。その場合は画面の「一括再取得」を押してよい。押しても止まったままなら、再連携が必要としてオーナーに報告する
- freeeの口座一覧には「同期失敗」件数・ステータス・最終同期日時と、口座ごとの同期ボタンがある（「全口座同期」は上位プラン限定）。APIには同期を起動する口も同期状態を返す項目も無い。freeeの同期ボタンは押さず、報告まで

### やること（freee・MF共通）

1. まず画面の「取得状態」を読む（最も確実）
2. 対象会社のAPI連携口座ごとに、取得できる最新の明細日付を見る（freee：`GET /wallet_txns`を口座別に集計、MF：`read <会社> "/transactions?..." --all-pages`を口座別に集計。`is_manual: false`が連携口座）
3. 動いていたはずの口座の最新明細が**30日以上前**で止まっている、または明細残高と帳簿残高の差が説明できないほど大きい場合は、連携切れ・同期停止の疑いとして、口座名・最新明細日を添えてチャット（と該当クライアントのSlackチャンネル）に報告する
4. 報告したうえで、手元の明細の範囲で自動処理を進める（止めない）。同期後に増えた分は次回の処理で拾う

## MFのレポートの金額の扱い

- 月次推移・試算表のレポート（`getReportsTransitionProfitLoss`・`getReportsTrialBalanceProfitLoss`）は**税抜（本体）**で返る。`is_tax_included: true`を渡しても数字は変わらない。**仕訳の金額（税込）と推移表の数字（税抜）を直接比べない**（「思ったより少ない＝登録に失敗した」と誤判定しかけた例がある）。税込で突合したいときは仕訳を引き、`value＋tax_value`を足す
- **部門別のPLは、補助科目の名前から組み立てない**。部門（department）と補助科目（プロジェクト）は別の軸で、補助科目の命名規則が部門と対応して見えても、名前で部門を推測して集計してはいけない（別部門の補助科目を含めて、黒字を赤字と報告した例がある）。MCPのレポートツールに部門の指定は無い。部門別を出す手段は、①画面の推移表を部門を指定して読む（確実）、②仕訳を引いて`department_name`で絞って自分で集計する、の2つ。**部門別の数字を報告する前に、必ず画面の推移表と突き合わせる**

## 月次処理を速くする分担

### 確認事項が複数出たら、聞く前にサブエージェントで並行して調べる

- 調べれば決まることを、1つずつ順番にオーナーへ聞かない。未仕訳の保留・要確認が複数あるときは、**サブエージェントを同時に出して並行で調べ、結果をまとめて1回で出す**。1体につき1論点で、論点どうしが独立していること
- サブエージェントへの指示に必ず入れる：
  - 冒頭で対象の会社名を伝え、`read`の結果の社名・事業者コードが指定と違えば何もせず報告して終わる
  - **読み取りのみ**。登録・書き換え・取引先作成・証憑の紐付けは呼ばない（登録は結果を見た本体が行う。判断が要る仕訳の登録をサブエージェントに任せない）
  - 根拠（仕訳番号・日付・金額・取引ID）を必ず添え、推測で断定しない
  - 大きな取得はファイルに保存されるのでPythonで解析する（`PYTHONIOENCODING=utf-8`・`PYTHONUTF8=1`）

### 役割分担の型（自前APIは会社を切り替えずに並行できる）

| 担当 | 仕事 |
|---|---|
| 本体 | 銀行・カード明細に紐づく未仕訳の登録、月次チェック、ログ・Slack |
| サブエージェント①（件数の多いもの） | 同じパターンの大量登録。10件ずつ登録→確認→結果ファイルに追記。会社をまたいで並行してよい |
| サブエージェント②（売上計上） | 証憑から作った仕訳案（明細に紐づかない登録）の登録。前月の同じ仕訳の組み方・IDに合わせる |

- 担当範囲をはっきり分ける（明細に紐づくもの／紐づかないもの）。登録の直前に毎回`read`で会社名を確かめ、違えば止める
- 大量登録は進捗を10件ごとにファイルへ書く作りにしておくと、止まっても続きから再開できる（`error-handling.md`の「1件登録→確認→次の1件」と両立させる）

### 時間を減らすコツ

- 準備は先に済ませる（証憑からの仕訳案、前月の同種仕訳の特定、入力JSONの型）
- 大きな取得はファイルに落としてPythonで解析する。`/journals`・`/transactions`は`--all-pages`で最後まで取る（付けずに取って残りのページがあると「1ページ目だけです」と出る）
- 過去パターンは「登録済み明細×仕訳」を`transaction_id`で結合して一括で出す。1件ずつ過去仕訳を引かない
- 月次チェックのPLは、試算表PLを月ごとに取れば仕訳から合成しなくてよい（会計年度内の月だけ有効）
- 補助科目のマイナスはツールが科目単位でしか見ないので、BS（`with_sub_accounts: true`）を見て手で拾い、発生元を期首からの仕訳でたどる
