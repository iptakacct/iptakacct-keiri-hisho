# 概要

マネーフォワード公式MCP（`mfc_ca`、claude.aiカスタムコネクタ経由）で、オーナーが`/mcp`で接続した会社の未仕訳を処理する自動処理スキル。

**運用の前提（重要な制約）**：
- **1回のセッションで扱えるのは1社のみ**。カスタムコネクタは「1接続＝1事業者」で、他社に切り替えるにはオーナーに`/mcp`で認証をクリア→再接続→事業者選択、を依頼する必要がある（このスキルからは認証操作を開始できない）
- 無人のスケジューラー実行は行わない。オーナーが会社を切り替えるたびに、このスキルの手順を最初から実行する
- **確認なしで自動登録する**のは、判定ロジックに完全一致する候補のみ。その代わり登録直後の検証と「チェック項目」を必ず行う
- **自動化率よりも誤登録リスク回避を優先する**。確信が持てないものは登録せず「要確認」に回す

## 会社→インスタンスの対応表

`config/mf-companies.json`（雛形は`config/mf-companies.example.json`）に、事業者名→インスタンス・ログ保存先・取引先対応表・Slackチャンネル・グループ間取引の有無を持つ。`mfc_ca_currentOffice`で取得した会社名をここと照合してインスタンスを判定する。

一致する会社が対応表に無い場合は処理を中止し、オーナーに確認する（対応表の更新漏れの可能性があるため）。

## 会社固有の確認済みパターンの置き場所

各インスタンスの`context/company/accounting-rules.md`の「自動仕訳の確認済みパターン」表に蓄積する。このSKILL.mdには会社固有の摘要・金額を書かない（型だけを書く）。

# 重要な設計方針

## AI提案仕訳のガードは使えない

`mfc_ca`のAPI（`getTransactions`・`postTransactionJournalize`）には、ブラウザ版の「作成される仕訳」に相当するAI提案科目の情報が含まれない。「MFのAI提案科目と一致するか」というガードは使えないため、代わりに**過去の登録済み実績**（処理E/F）と**確認済みパターン表**を根拠にする。

## 処理A：支払手数料の判定ロジック（摘要文言＋確認済みパターンのみ）

1. `mfc_ca_getTransactions`（`journalizing_statuses: ["none"]`）で未仕訳明細を取得する。日付範囲は前回処理日〜当日を目安に指定する（`start_date`と`end_date`の差は366日以内という制約に注意）
2. 各明細について、以下いずれかを満たせば「支払手数料」で登録候補とする。**account_idは会社ごとに異なるため、都度`mfc_ca_getAccounts`でその会社の「支払手数料」（販売費及び一般管理費区分）のaccount_idを確認してから使う**（`（外）`が付く同名の別科目〔営業外費用区分〕と取り違えないこと。他社で使ったIDを流用しない）
   - a. 摘要（`content`）に「テスウリヨウ」「手数料」「IB基本料」等、手数料であることを示す文言が含まれる
   - b. 摘要に文言が無くても、そのインスタンスの`accounting-rules.md`の確認済みパターンと摘要・金額が完全一致する
3. いずれにも該当しない場合は登録せず、要確認ログに理由付きで記載する
4. 登録は`mfc_ca_postTransactionJournalize`（`account_id`＋`transaction_id`のみ指定。`tax_id`は明示せず勘定科目のデフォルトに委ねる＝通常「課税仕入10%」が自動適用される。初回は結果を確認する）
5. **1件ずつ登録→レスポンスで登録内容（借方・貸方・金額・税区分）を確認→次の1件、のサイクルを徹底する**（`error-handling.md`の原則）

# 実行手順

1. `claude mcp list`で`mfc_ca`関連の接続状態を確認する。未認証の場合、オーナーに`/mcp`での認証を依頼する
2. `mfc_ca_currentOffice`を呼び、接続先の会社名を対応表と照合してインスタンスを判定し、チャットに一言報告する。対応表に無い会社の場合は処理を中止する
3. `mfc_ca_getConnectedAccounts`で銀行口座連携の状態を確認する。連携エラー・停止中の口座があれば、対象会社名とエラー内容を全体通知チャンネルに投稿する。正常なら何も投稿せず次に進む
4. `mfc_ca_getTransactions`で未仕訳を取得し、処理A〜Fの候補を抽出する
5. 判定ロジックに完全一致する候補は、確認を挟まず登録する。登録直後に該当仕訳を再取得し、借方・貸方・金額・税区分が意図通りかを確認する（誤登録の即時検知）。一致しない・確信が持てないものは「要確認」に回す（回す前に、下記「要確認案件の裏取り」が使えないか検討する）
6. 「チェック項目の実行」（下記）を行い、登録件数・要確認件数・チェック結果をオーナーに報告する
7. 登録結果を、判定したインスタンスのログファイル（対応表の`log_file`）に追記する
8. 登録件数・要確認一覧・チェックで引っかかった点を、判定したインスタンスのSlackチャンネルに投稿する

# 処理B〜F（会社ごとに勘定科目IDが異なるので、毎回getAccountsでの確認が必要）

**重要な前提**：勘定科目ID・補助科目ID・税区分IDは**会社ごとに完全に別物**。毎回`mfc_ca_currentOffice`で接続先を確認した上で、その会社の`mfc_ca_getAccounts`／`mfc_ca_getSubAccounts`でIDを都度取得する。`getAccounts`の出力は大きいので、トークン超過で保存されたファイルをgrepで検索する（「技術メモ」参照）。

**取引先対応表の活用**：処理B・Cで摘要から取引先を特定する際は、まずインスタンスの取引先対応表（対応表の`trade_partner_map`。銀行データの表記↔会計上の取引先・補助科目の対応を会社ごとに蓄積したもの。法人格略語の読み替えは`company-name-abbreviations.md`）を確認する。載っていれば毎回`getJournalById`等で調べ直す必要はない。表に無い新しい対応が判明したら、その都度追記して育てていく。

## 処理B：未払金の消込

1. `mfc_ca_getJournals`（account_id=未払金、直近1〜2ヶ月）で全件取得する
2. 貸方（計上）と借方（消込）を金額で突合し、消込先が見当たらない貸方エントリ（＝まだ未消込の未払金）を抽出する。同一金額が複数ある場合は誤突合のリスクがあるため、疑わしい場合は開いたまま扱う（安全側に倒す）
   - **プール型補助科目（「月末振込」「10日振込」等）の場合**：単発の貸方エントリと1対1で一致しないことが多い。同じプール補助科目の貸方エントリを日付（計上月）でグルーピングして合計し、その合計額が出金取引の金額と一致するか確認する。支払サイトが1〜2ヶ月ずれることがあるため、2〜3ヶ月分のプール計上を確認する
3. 開いたままの貸方エントリの金額・日付と、未仕訳の出金取引を照合する。摘要だけで取引先を特定できない場合は取引先対応表→`mfc_ca_getJournalById`で計上仕訳の**借方側**（費用科目側）の補助科目・取引先名を確認する（未払金側自体は補助科目なしのことが多い）。それでも確信が持てない場合はオーナーに確認する
4. **未払費用や預り金に計上されているケースもある**（役員報酬バッチの中の未払役員報酬、住民税の預り金等）。未払金だけでなく、明細の内容から関連しそうな他の負債科目も確認する
5. 登録は`mfc_ca_postTransactionJournalize`（account_id=未払金等、sub_account_idは**計上時の該当側と同じもの**を使う。計上時が補助科目なしならこちらも補助科目なし）

## 処理C：売掛金の消込

処理Bと対称的に、account_id=売掛金で借方（発生）・貸方（消込）を突合する。

## 処理D：グループ会社間資金融通（対応表で`intercompany_transfers: true`のインスタンスのみ）

1. 処理B/Cで一致しなかった入出金取引について、摘要がグループ内の処理中の会社「以外」を指しているか確認する（`accounting-rules.md`に記録した各社のエイリアス・紛らわしい別法人の注意を踏襲する）
2. `mfc_ca_getSubAccounts`（出金なら account_id=未収入金、入金なら account_id=未払金）で該当会社名の補助科目が実在するか確認してから使う（「㈱〇〇」表記と表記なしの2種類が両方存在することがある＝取り違え注意）
3. `postTransactionJournalize`で登録する（出金取引→未収入金・sub_account_id=相手会社、入金取引→未払金・sub_account_id=相手会社）
4. **会社間の対応関係に気づける**：ある会社で処理Dとして登録した取引の相手方は、別の会社側の未仕訳リストに「対になる取引」として同じ日付・同額で現れることが多い。複数社をまたいで処理する際は、前に処理した会社の登録内容を覚えておくと、次の会社での判定が即座にできる

`intercompany_transfers: false`のインスタンスでグループ会社間の資金融通が疑われる取引が出てきた場合は、自動登録せず「要確認」として記録する。

## 処理E/F：確認済み摘要パターンの自動登録（過去の登録実績を根拠にする）

1. `mfc_ca_getTransactions`（`content`=摘要文言、`journalizing_statuses: ["registered"]`、過去6ヶ月程度）で、同じ摘要パターンの過去の登録済み取引を検索する
2. 複数ヶ月分ヒットした場合、それぞれの`transaction_id`を`mfc_ca_getJournals`（`transaction_ids`指定。**配列で複数一括指定するとエラーになるので1件ずつ呼ぶ**）に渡し、実際に使われた勘定科目・補助科目を確認する。**全期間で同一科目だったことを確認してから**、今回の未仕訳にも同じ科目を適用する（「摘要は同じでも金額は毎月変動、勘定科目は固定」という型。利息・元金返済・保険料・ファクタリング等が典型）
3. **重要な制約：分割仕訳（1つの取引が複数の勘定科目に分かれる仕訳）は`postTransactionJournalize`では登録できない**（1回の呼び出しにつきaccount_idを1つしか指定できないため）。過去仕訳の`branches`が2つ以上、またはbranch内の`debitor`が複数科目にまたがっている場合は、自動登録せず「要確認」として記録する（リース料が複数機器に分かれるもの、家賃＋振込手数料の2科目に分かれるもの等が典型）
4. 確認できたパターンは、そのインスタンスの`accounting-rules.md`の確認済みパターン表に追記する

## 処理G：クロスカンパニー引き継ぎ（対応表で`cross_company_handoff_file`があるインスタンスのみ）

グループ内で「A社側の原価計上」と「B社側の売上計上」が対になる仕訳を毎月登録する必要がある場合の型。1回のMCP接続では1社にしか繋がらないため、**A社接続時に計算した内訳を引き継ぎファイルに保存し、次にB社に接続したタイミングで自動的に反映する**。

- 計算基準・仕訳型は`accounting-rules.md`に記載する
- 引き継ぎファイルは対象月ごとに行を分け、状態（未計上／計上済み）と両社の仕訳Noを記録する
- 後日「要確認」分が登録されて対象月の数字が変わった場合、次回接続時に差分を確認し調整仕訳を検討する

# 預金利息入金の登録（「2仕訳方式」）

源泉税逆算方式（入金額から総額・源泉税額を逆算し、借方:普通預金＋法人税等〔利息源泉〕／貸方:受取利息〔総額〕で計上）をMCP経由で行う場合の技術的注意。

## 重要な制約：分割仕訳とtransaction連携は両立しない

- `postTransactionJournalize`：明細（`transaction_id`）に紐づけて仕訳を作る。明細が「仕訳済み」になるが、**account_idを1つしか指定できず分割仕訳を作れない**
- `postJournals`：`branches`を複数指定できるが、**`transaction_id`を持たない＝明細とは紐づかない**。これだけで登録すると元の明細が未仕訳に残り続け、二重計上リスクが生じる
- 明細を「対象外」にする、削除する、明細と仕訳を事後的に紐づけるAPIは**mfc_caに存在しない**。`putJournals`の`branches`を空配列にすることも拒否される＝一度作った仕訳は空にも削除にもできない

## 確立した方式

1. `postTransactionJournalize`（account_id=受取利息、sub_account_idは下記の判定基準で選択）で明細を**入金額のまま**登録する
2. 別途`postJournals`で、差額分（源泉税額）だけの仕訳を1本追加する：借方=法人税等（利息源泉所得税）／貸方=受取利息（同じsub_account_id、源泉税額）。摘要に「◯◯　利息源泉税分」のように明記する
3. 結果として受取利息が2つの仕訳に分かれるが、実害はない
4. **1本化しようとしてはいけない**。分割・統合を試みると、差額仕訳側を消せず二重計上になる。**transaction紐づき仕訳を最終形にし、差額仕訳側は最初から最後まで「差額のみ」の内容で固定しておく**

## 源泉税額の逆算

- 国税15.315%（所得税15%＋復興特別所得税0.315%）を入金額から逆算する。1円未満切り捨てのため、`floor(total*0.15315) = total - deposit`を満たす`total`が複数候補になることがある。通知書等の裏取りができない場合は**小さい方の候補**を採用する（`accounting-rules.md`で別の指定があればそれに従う）

## 受取利息の補助科目・源泉税の相手科目（会社ごとに構成が異なるので都度確認）

- 摘要が「決算利息」「ケツサンリソク」の場合 → その会社に「決算利息」という補助科目があればそれを使う。無ければ「預金利息」（汎用）
- それ以外は`mfc_ca_getConnectedAccounts`で連携元銀行を確認し、専用の補助科目（銀行名）があればそれを、無ければ汎用の「預金利息」
- **源泉税の相手科目（借方側）は会社によって`租税公課`／`法人税等`／`法人税、住民税及び事業税`など全く別の科目に置かれている**。同名の補助科目が複数科目に存在することもある。**会社を切り替えるたびに`getAccounts`で「利息源泉」を検索し、その会社の実際の構成を確認してから登録する。他社の実績を流用しない**

# 要確認案件の裏取り

判断に迷う仕訳が出た際、オーナーに確認する前に、判断材料を増やせる手段：

1. **過去仕訳の検索**（最優先）：同じ摘要・取引先の過去の処理を`getTransactions`（registered）→`getJournals`で確認する
2. **取引先対応表・accounting-rules.md**：既に記録済みの対応・ルールを確認する
3. **ローカルに蓄積されたクライアントSlackログ**（インスタンスの`work/`配下に収集されている場合）：取引先との合意事項・社内の判断メモを検索する
4. **クライアントのSlackワークスペースを直接検索**：claude.aiのSlackコネクタは1接続＝1ワークスペースなので、切り替えにはブラウザ操作とオーナーの立ち会いが必要。他の処理にも影響するグローバルな状態変更なので、切り替える前・元に戻す前にオーナーに一言確認する。ワークスペース名→会社の対応表はインスタンスの`context/company/`に記録して育てる

# チェック項目の実行

登録後チェックは、確認省略の代わりの安全弁として実行する。

1. `check-items-common.md`（全社共通）の項目を、その回に登録した仕訳に対して実行する
2. インスタンスの`accounting-rules.md`に会社固有のチェック項目があれば、それも実行する
3. 引っかかった項目があれば、登録済みの仕訳を勝手に訂正せず、オーナーへの報告に明記する

# 技術メモ

- `getAccounts`は会社によっては出力がトークン上限を超え、自動的にファイル保存される。その場合はPythonで該当ファイルを`encoding='utf-8'`で読み、目的の科目名を`re.finditer`で検索し、前後の文字列を**別のファイルに`utf-8`で書き出してからReadツールで読む**（Bashのstdoutに直接printすると文字化けする＝Windows環境のシェル既定エンコーディングの問題）
- `getJournals`の`transaction_ids`は複数指定するとAPIエラーになる。1件ずつ渡す
- `getTransactions`の`per_page`は最小10・最大500
- **`putJournals`で借方・貸方が対になっている単一branchを編集する際**：同一branch内は`debitor.value`と`creditor.value`が一致していなければならない。片方だけ変えると、MFは貸方側の値に借方側を自動的に揃える（税区分の再計算はされず古い`tax_value`が残る）。account_idだけ変えたいときも、変更後のvalueは両側で揃えて明示的に指定する
- **内税入力・自動仮受消費税/仮払消費税処理**：`postJournals`/`putJournals`への入力時は課税対象行に**税込金額**をvalueとして渡す。登録後、MF側が本体（税抜）と消費税に分解し、`getJournals`で読み返すと課税対象行の`value`は税抜、`tax_value`はその消費税額として返る。**借方合計＝貸方合計の検算は、課税科目を`value＋tax_value`で合計してから比較する**。value同士だけを比較すると正しい仕訳を「不整合」と誤診断する
- 仕訳の`number`（取引No.）は会計期間ごとにリセットされる。複数期間のデータをマージするときは`id`をユニークキーにする

# 今後の課題

- 処理B〜Dの判定ロジック（貸方・借方突合、プール合計照合）のスクリプト化
- 要確認ログの仕組み化（現状は手動でログファイルに追記）
- 無人化：事業者切替をオーナーが`/mcp`で操作する前提のため当面見送り。Slack通知でトリガーし操作を待って再開する半自動フローは構想のみ
