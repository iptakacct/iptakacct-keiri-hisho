# 目的

複数社のBPOで蓄積した知見を、次のクライアントで最初から使える形にする。自動コピーではなく、差分を読んで汎用化する半自動の作業。

# 手順

1. 対象の変更を把握する。週次報告を受けた場合はその候補一覧、依頼が「先週分」なら `bash .claude/scripts/weekly-template-review.sh --diff` で差分本文を出す（Slack投稿はしない）。特定の変更を指されたらそれだけを読む
2. 候補ごとに、蓄積先を決める：
   - **振る舞い・手順・ツールの癖**（「〇〇はこう操作する」「△△は通知されない」「この仕訳はこう切る」）→ 共通 `.claude/rules/`（既存ファイルの該当節に追記。無ければ新設）または該当共通スキルの `SKILL.md`。既存インスタンスにも即時に効く
   - **骨組み・項目・型**（新しい種類のシステム、`accounting-rules.md`／`systems.md`に足すべき見出し・行、「接続時の動き」の型）→ `テンプレート/` の該当ファイル。新規インスタンスに効く
   - どちらでもない（その会社だけの事実）→ 反映しない
3. 汎用化の規則：
   - 社名・人名・ID・チャンネルID・金額・フォルダIDは入れない。実例として価値があれば「例：ある会社では…」の一般形にする
   - 「YYYY-MM-DD、〇〇の指示で」の経緯は原則削除し、ルール本文だけ残す。失敗の教訓は固有名詞を伏せて残す
   - 会社ごとの確認済みパターン・除外設定は移植しない（各インスタンスの `accounting-rules.md` に蓄積する型を保つ）
   - テンプレの雛形には「（未設定・実務の中で判明次第追記）」の型を守る
4. `テンプレート/` を編集したら、`テンプレート/` にテストデータ・実データが紛れていないか一読する（常にまっさらである前提）
5. コミットしてpushする（`git add` はパス明示、`-a` は使わない）。メッセージ例：`template-sync: <要約>（<元インスタンス>の知見を汎用化）`
6. 反映した件数・見送った候補と理由をチャットで報告する。判断に迷ったものは書かずに「保留」として報告し、オーナーに確認する

# 注意

- インスタンス側のファイルは書き換えない（元の記録はそのまま残す）
