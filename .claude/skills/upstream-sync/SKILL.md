name: upstream-sync
description: 「上流の変更を取り込んで」「開発元の更新を反映して」「upstream sync」のように言われたら使う。開発元（上流）リポジトリで manifest.json 対象パスに入った変更を読み、クライアント固有情報を除いて汎用化した形でこのリポジトリへ移植し、leak-scan を通してからコミットする。
---

# 目的

上流（開発元の実運用リポジトリ）で日々改善されたスキル・ルール・hooksを、固有情報を混入させずにこの汎用版へ還流させる。自動コピーではなく、差分を読んで汎用化する半自動の作業。

# 前提

- `upstream/local.json` に上流のローカルパスがあること（無ければオーナーに確認して止まる）
- `tools/leak-scan.py` が固有語リストを読める状態であること（`python tools/leak-scan.py` の1行目に「固有語N語」と出る。0語なら固有語リストの場所を確認する）

# 手順

1. `bash tools/upstream-diff.sh` を実行し、未同期のコミット一覧と変更ファイルを把握する。0件なら「未同期なし」と報告して終了
2. `bash tools/upstream-diff.sh --patch` で差分本文を読む。長い場合はファイルに落として読む
3. 変更ファイルごとに `upstream/manifest.json` の該当 `mappings` を見つけ、`note` の汎用化方針に従って **こちら側の `dst` ファイルを編集する**（上流ファイルを丸ごとコピーしない）
   - 呼称：「（オーナーの実名）さん」→「オーナー」、秘書名→「秘書」
   - クライアント名・会社名・SlackチャンネルID・ユーザーID・会社IDは除去する。実例として価値がある場合は「例：ある会社では…」の一般形にする
   - 「YYYY-MM-DD、○○の指示で追加」等の経緯は原則削除し、ルール本文だけ残す。失敗の教訓は固有名詞を伏せて残す
   - 会社ごとの確認済みパターン・除外設定は移植せず、「各インスタンスの `context/company/accounting-rules.md` に蓄積する」型を保つ
   - `excluded` に該当するファイルは触らない
4. `manifest.json` に無い新しいファイルが上流で増えていた場合：汎用に値するか判断し、値するなら `mappings` に追加して移植、しないなら `excluded` に理由付きで追加する
5. `python tools/leak-scan.py` を実行し、検出ゼロになるまで修正する（例示で必要な場合のみ行末に `leak-scan:allow`）
6. 移植したPythonスキルがあれば、そのディレクトリの `pytest` を実行する
7. `manifest.json` の `last_synced_commit` を上流の現在のHEAD（`git -C <上流> rev-parse --short HEAD`）に更新する
8. `upstream/sync-log.md` の先頭に、日付・取り込んだ内容の要約・見送った変更と理由を追記する
9. コミットする（pre-commitで leak-scan が再度走る）。コミットメッセージ例：`upstream-sync: <上流コミット範囲> の変更を取り込み（<要約>）`
10. 結果（取り込んだファイル数、見送り件数、leak-scan結果）をオーナーに報告する

# 注意

- **上流のファイルをそのまま `cp` しない**。必ずこちらの既存ファイルに差分を当てる形で編集する（こちら側で既に汎用化済みの文言を上書きで戻してしまうため）
- leak-scan が通らない状態でコミットを試みない。`--no-verify` は使わない
- 判断に迷う変更（汎用か固有か）は移植せず、`sync-log.md` に「保留」として書き、オーナーに確認する
